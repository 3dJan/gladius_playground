## Plan: Strict Desktop/VR Workspace Split

Build a native VR workspace as a separate composition root from the existing desktop UI. `DesktopWorkspace` will continue to own `MainWindow`, Dear ImGui, `ModelEditor`, `NodeView`, GLFW, desktop cameras, dialogs, and desktop presentation. `VRWorkspace` will own native spatial UI, controller/gaze interaction, OpenXR timing, stereo presentation, and VR haptics. Both roots will consume one UI-independent workspace kernel containing document state, graph mutation transactions, validation, immutable evaluation snapshots, backend-neutral render services, selection/navigation state, and capability reporting. The first implementation permits only one interactive authoring workspace at a time; it does not add `isInVrMode` branches throughout desktop code or allow two independent writers to mutate the same document concurrently.

The plan treats the supplied haptic concepts as interaction policies over neutral commands. OpenXR haptic calls remain inside the XR-owned thread and adapter. The existing OpenCL backend remains the production default until the pure-WebGPU profile, native Dawn/OpenXR interop, and stereo lifetime rules are proven.

**Steps**

### Phase 0 — Lock product boundaries and feasibility gates

1. Define the first VR milestone as a native spatial vertical slice: stereo model preview, room/world anchoring, controller aim/select/grab/recenter, spatial parameter/control panels, a controller-attached inspection mode, and a desktop mirror or diagnostic fallback. The primary VR controls must be spatial scene elements, not a floating Dear ImGui application and not screen-space `imgui-node-editor` hitboxes projected into 3D.
2. Keep the existing desktop authoring workflow intact: Dear ImGui, `ModelEditor`, `NodeView`, desktop file/resource dialogs, keyboard shortcuts, desktop gamepad navigation, and the current desktop render presenters remain the primary desktop UI.
3. Make authoring workspaces mutually exclusive for the first implementation. `WorkspaceHost` selects one active writer—desktop or VR—and the inactive root is not an interactive second editor. A workspace switch must finish or cancel open edit transactions, stop/retain its presentation resources according to ownership rules, and publish a consistent snapshot before the next root becomes active. A read-only mirror can be added later, but simultaneous interactive editing is out of scope here.
4. Establish build and include boundaries before adding features. The shared target may include document/nodes, neutral workspace services, neutral render/evaluation contracts, and backend interfaces; the desktop target may include ImGui/GLFW and desktop UI; the VR target may include spatial UI and interaction; the optional XR target may include OpenXR headers, handles, and native calls. Shared code must not include ImGui, GLFW, OpenXR, desktop widgets, or headset-specific haptic types.
5. Run a native interop spike in parallel with the shared-workspace extraction. On the target Linux graphics stack, enumerate OpenXR system/view configuration/reference spaces, create a session, acquire/release a color swapchain image, and record native image formats, array/layer requirements, color space, and graphics binding details.
6. Test whether the selected Dawn backend can render to or import the acquired OpenXR images without CPU readback. Accept only a direct Dawn/native-image path or a lifetime-safe native GPU bridge for production; classify CPU readback as diagnostic-only and classify unsupported adapter/runtime combinations as unavailable rather than silently switching to OpenCL.
7. Record the target runtime, graphics API, OpenXR extensions, refresh modes, near/far range, depth-composition support, eye-tracking support, and mirror policy as capability/profile data. Do not encode these assumptions into the shared render contracts.

### Phase 1 — Extract the shared workspace kernel

1. Add a UI-independent `WorkspaceServices` composition. It should provide a shared `Document`/assembly identity, graph mutation service, parameter-edit service, transaction-aware history, validation and issue state, refresh/evaluation coordination, immutable snapshot factories, selection, function navigation, backend runtime/session, bounds/SDF sampling, and capability reporting. It may initially wrap existing `Document` methods rather than immediately splitting `Document` into many classes.
2. Add a `WorkspaceHost` that constructs the shared services once and selects `DesktopWorkspace` or `VRWorkspace`. The host owns lifecycle and active-workspace policy; neither workspace should construct a competing document/evaluation backend. Keep compatibility accessors such as `Application::getMainWindow()` only as transitional forwarding APIs while ownership moves to the desktop root.
3. Define stable-ID command and event contracts. Commands should carry document identity, function/node/port/parameter/resource IDs, transaction ID, and the expected generation where needed; they must not carry ImGui IDs, screen coordinates, OpenXR handles, live GPU objects, or raw pointers across workspace/thread boundaries.
4. Implement a `GraphMutationService` façade around the current `Model`, `Assembly`, and `Document` operations. It must cover node creation/deletion, port linking/unlinking, type updates, function-call rebinding, extraction, library merge/resolve, resource changes, and grouped compound edits. Each command acquires the assembly lock, validates before mutation, applies atomically, updates graph/type/flat-assembly state, increments the appropriate structural generation, and emits one logical mutation result.
5. Implement a `ParameterEditService` with explicit `beginParameterEdit`, `updateParameterPreview`, `commitParameterEdit`, and `cancelParameterEdit` phases. Continuous controller or slider movement must not create one undo item per frame. Commit creates one before/after transaction; cancel restores the preview state. Separate persistent parameter edits from render-only settings such as slice height, cutoff, field visualization, and quality controls so view changes do not rebuild the document scene.
6. Wrap `nodes::History` in a transaction-aware history service. Compound operations such as create-with-links, delete-with-dependent-links, extraction, library import, multi-parameter edits, and depth-clutch dragging produce one history item. Undo/redo must enter the same mutation, validation, refresh, generation, and notification pipeline as forward edits; no workspace may assign directly to a live `Assembly` behind that pipeline.
7. Centralize validation and refresh/evaluation policy. Preserve the existing distinctions between structural edits, parameter edits, view/pose changes, and render-setting changes. The coordinator owns structural edit epochs, parameter/resource/evaluation generations, debounce, cancellation, stale-result rejection, compilation/evaluation scheduling, and follow-up work. Invalid graphs must be rejected before GPU submission.
8. Add backend-neutral `SelectionService` and `FunctionNavigationService`. Selection stores stable node/link/port IDs, active function scope, primary selection, and a generation; navigation stores stable function IDs and back/forward history. Screen positions, node-editor handles, canvas pan/zoom, and clipboard state remain desktop-only.
9. Require asynchronous workers to consume immutable document/evaluation/render snapshots. Preserve `SaveSnapshot`, `RenderSceneSnapshot`, and `RenderRequest` as separate consumer contracts. Any submitted Dawn/OpenCL work retains its resources until a terminal event even when its result becomes stale.
10. Define service notifications for document identity changes, structural mutations, parameter transactions, validation issues, snapshot availability, capability changes, and terminal evaluation/render results. Desktop and VR may present these notifications differently, but neither may invent a second evaluation or undo pipeline.

### Phase 2 — Migrate and preserve the desktop composition root

1. Introduce `DesktopWorkspace` as the desktop composition root. It owns `MainWindow` and all desktop-only services, while receiving `WorkspaceServices` from `WorkspaceHost`. `Application` should stop being the implicit owner of both application-wide workspace state and desktop widgets; during migration, forwarding methods preserve MCP and legacy callers.
2. Keep `MainWindow` responsible for Dear ImGui/GLFW setup, menus, dialogs, welcome screen, desktop file operations, keyboard shortcuts, desktop gamepad UI, status/diagnostic overlays, and desktop presentation. Do not add OpenXR includes, VR branches, headset transforms, or haptic-device logic to `MainWindow`, `GLView`, `ModelEditor`, or `NodeView`.
3. Convert `ModelEditor`, `NodeView`, `ResourceView`, and related desktop gesture handlers into adapters over shared commands. Replace direct calls such as `Model::addLink`, `Model::remove`, direct parameter mutation, and ad-hoc `markModelAsModified`/history updates with service transactions while preserving current 2D graph behavior and node-editor layout.
4. Keep `LinkDragState`, `imgui-node-editor`, `OrbitalCamera`, desktop clipboard/layout/focus state, and `ParameterThrottle` in the desktop target. Their semantics can inform VR interaction policies, but their types must not leak into shared services or `VRWorkspace`.
5. Extract the neutral portion of `RenderWindow` into a UI-independent render workflow service. Move or re-home `NeutralRenderScheduler`, `NeutralFrameSubmissionTracker`, `RenderWorkflowController`, and related request/freshness policy out of a desktop-only dependency path, retaining compatibility includes only as a temporary migration aid. The desktop adapter continues to own camera input, ImGui overlays, texture upload, and window presentation.
6. Verify that the desktop root still has identical document editing, undo/redo, parameter throttling, save/load, render invalidation, and fallback behavior after the service migration. This phase must be usable without OpenXR installed.

### Phase 3 — Unify backend-neutral evaluation and render contracts

1. Evolve `ApplicationComputeRuntime`/`IBackendRuntime` from a migration seam into the shared backend service composition consumed by both workspace roots. Expose narrow scene compilation, immutable parameter/resource snapshots, bounds, SDF sampling, render-session, capability, and terminal-submission services; keep `ComputeCore` as an OpenCL compatibility seam only until all consumers migrate.
2. Keep OpenCL as the default production backend. An explicit WebGPU request must either construct a valid WebGPU runtime or report an unavailable/error state; it must never silently fall through to OpenCL. The selected workspace must not affect backend selection.
3. Complete the declared pure-WebGPU analytic/non-NanoVDB profile before calling the VR renderer production-ready. Cover projection/ray setup, adaptive stepping/refinement, normals, lighting/AO/shadows/fog/clipping, overlays, object color/type, packing, supported graph nodes, mesh/resource payloads, and capability diagnostics. Keep VDB/NanoVDB and unsupported resource classes capability-gated.
4. Harden `WebGPUComputeContext` and all consumers: every Dawn instance/device/queue access takes `DeviceLock`, error scopes and device-loss state are observable, adapter limits are negotiated, mapping/readback has deterministic timeout/failure behavior, and buffers/textures/pipelines remain alive until terminal completion. Avoid unsafe unsigned FWN pruning near surfaces; use a validated conservative bound or disable that optimization.
5. Extend `RenderContracts` additively with XR-neutral `RenderView`, asymmetric projection/tangents, view pose/basis, per-view viewport, `RenderViewSet`, predicted display time, display-frame identity, pose/view generations, `RenderTargetDescriptor`, optional output channels, and stereo-pair freshness. Do not include OpenXR structs, Dawn handles, GLFW types, or headset-specific enums.
6. Preserve mono desktop behavior through a desktop-to-one-view adapter. Add a stereo acceptance policy to the existing neutral scheduler/tracker so both eyes share scene, parameter, resource, evaluation, pose, target, display-frame, and relevant viewport generations. A completed left eye must never pair with a stale right eye; a failed or cancelled eye invalidates the pair while physical GPU work remains retained.
7. Add a deterministic mock XR contract/runtime without OpenXR linkage. Model runtime absence, session transitions, predicted time, asymmetric views, `shouldRender=false`, invalid poses, swapchain acquire/wait/release, session loss, device loss, and shutdown. This is the primary test seam for the frame loop and stereo freshness rules.

### Phase 4 — Add the optional XR runtime and presentation boundary

1. Add an optional native-only `GLADIUS_ENABLE_OPENXR` configuration. Update `/home/jan/projects/gladius/gladius/CMakeLists.txt`, `/home/jan/projects/gladius/gladius/src/CMakeLists.txt`, a future `/home/jan/projects/gladius/gladius/src/xr/CMakeLists.txt`, and `/home/jan/projects/gladius/gladius/vcpkg.json.in` through the repository’s normal configuration flow. Ordinary desktop, WebGPU-without-XR, browser, headless, and MCP builds must not require OpenXR.
2. Implement an `IXRRuntime`/neutral XR contract and an `OpenXRSession` adapter. The adapter owns instance/system discovery, extension negotiation, view configuration, reference spaces, session events, frame timing, action spaces, and orderly shutdown. Native OpenXR handles stay private to the adapter.
3. Make the XR owner thread explicit. `waitFrame`, `beginFrame`, view location, action polling, haptic output, swapchain acquire/wait/release, and `endFrame` are issued by the XR owner loop. GPU worker threads and shared workspace services may enqueue neutral work or haptic commands but must never call OpenXR.
4. Implement the XR frame sequence: poll events, wait frame, begin frame, locate both views at predicted time, sample actions/poses, acquire and wait for target images, build a paired render request, submit or safely skip when `shouldRender` is false, wait for the required terminal GPU state, end the frame with a complete projection layer, and release images according to the proven ownership bridge.
5. Add `XrSwapchainPresenter` beside `WebGPUFramePresenter`, not inside it. Preserve native image identity, array layer, format, dimensions, color space, and swapchain generation. Retain acquired images and bridge resources through terminal completion; recover deterministically from timeout, format mismatch, session loss, device loss, resize, and unsupported image import.
6. Add a desktop mirror as an independent target that displays one eye or a diagnostic composite. It must not force the final XR images through the CPU readback path and must not make desktop ImGui the VR presentation path.
7. Add depth composition only after stereo color submission works. Generate depth with exact asymmetric per-eye projection and runtime near/far mapping; advertise color-only presentation when the depth extension or implementation is unavailable.

### Phase 5 — Implement `VRWorkspace` and native spatial interaction

1. Add `/home/jan/projects/gladius/gladius/src/vr/VRWorkspace.*` as a separate composition root. It consumes `WorkspaceServices` and neutral XR/runtime interfaces, owns spatial scene composition and interaction state, and never includes `MainWindow.h`, `ModelEditor.h`, `NodeView.h`, `imgui-node-editor`, or desktop dialog types.
2. Build a native spatial UI layer for the first milestone: world-anchored model controls, left-side palette/control surfaces, parameter widgets, function navigation, selection feedback, recenter/status controls, and accessible controller-ray hit targets. UI geometry, transforms, text, hit testing, and panel composition live in VR-specific code; graph/document mutations are submitted as shared commands.
3. Add dedicated XR input types modeled after the raw-state/action/dispatch separation of `GamepadState`, `GamepadActionMap`, and `GamepadActionDispatcher`, but containing timestamped aim/grip poses, handedness, tracking validity/confidence, select/squeeze/menu/cancel/recenter actions, thumbsticks, and haptic output capabilities. Do not reuse `GamepadState` as the XR state model.
4. Implement `XrRayInteractor` and a VR interaction state machine for hover, select, grab, cancel, recenter, model orbit/pan/scale policies, world anchoring, and controller-attached inspection. Keep interaction transforms separate from render-camera transforms and reject actions from invalid or stale poses.
5. Implement depth-clutch numeric editing through the shared parameter transaction service: trigger begins a transaction, lateral motion updates a preview, bounded controller depth changes sensitivity, release commits once, and cancel rolls back. Add unit-aware precision, dead zones, sensitivity limits, visual state, and an accessibility alternative.
6. Add optional gaze arbitration and dimming only when tracking validity is explicit. Controller-ray focus must remain usable during gaze loss. Never infer a blink from generic gaze dropout; valid blink/pupil extensions may only trigger opportunistic low-priority work.
7. Defer complete 3D force-directed graph authoring, capsule-wire rendering, and spatial graph telemetry until the native spatial panel and shared command pipeline are proven. When added, graph geometry and hit testing must be VR-native and must not adapt screen-space `imgui-node-editor` internals.

### Phase 6 — Add neutral haptics and OpenXR output

1. Add neutral haptic contracts, preferably under `/home/jan/projects/gladius/gladius/src/interaction/` or another UI-independent module. Define `HapticHand`, cue categories, `HapticCommand`, capability data, `IHapticSink`, and a scheduler queue. A command includes finite duration, clamped amplitude, frequency where supported, priority, source/cue identity, issue time, workspace/document/evaluation generation, and optional cancellation/source group.
2. Implement `HapticScheduler` with a deterministic clock/test seam. It must rate-limit and coalesce repetitive commands, deduplicate state-transition cues, prioritize safety/commit feedback over low-priority ambience, clamp device limits, drop stale generations, stop sources on release/cancel/session loss, and never block the evaluation or GPU worker thread. Desktop and mock environments use a null/fake sink.
3. Implement `OpenXRHapticOutput` behind the XR owner thread. Translate neutral hand/cue commands to negotiated haptic actions and subaction paths, verify controller/action support, convert finite seconds to `XrDuration`, and use explicit stop calls for source cancellation. Do not use `XR_INFINITE_DURATION` for short pulses merely because the sample API accepts a duration parameter.
4. Implement the SDF surface detent as a VR interaction policy over a generation-aware `SdfSampleRequest`/`SdfSampleResult`. Sample the controller tip from the shared evaluation service, reject results older than the current pose/evaluation generation, use signed-distance bands with hysteresis, and emit low-frequency proximity ticks whose cadence/amplitude increase only within bounded limits. Do not make surface feedback depend on an unsafe unsigned-distance FWN shortcut.
5. Implement socket snap feedback through neutral `SocketInteractionEvent` states. Use shared `Model::isLinkValid`/candidate semantics through `GraphMutationService`; emit one enter/snap pulse, avoid repeated hover pulses through the scheduler, and distinguish commit/reject/cancel feedback. The event must reference stable port/parameter IDs rather than desktop node-editor IDs.
6. Implement depth-clutch friction through neutral `NumericInteractionEvent` threshold crossings. Emit haptic ticks with amplitude/frequency and cooldown derived from macro/micro depth mode, include hysteresis so values hovering around a threshold do not chatter, and stop the source on commit/cancel/interaction loss.
7. Reserve the functional data-flow pulse for the later native spatial graph phase. Define a future `DataFlowSample` contract containing edge identity, validated signal magnitude/frequency, telemetry generation, and timestamp, but do not synthesize pulses from unvalidated or unavailable graph telemetry in the first VR slice.
8. Add haptic capability/status reporting to the VR diagnostics. Missing haptic actions, disconnected controllers, unsupported frequency control, session focus loss, and stale telemetry must degrade to no feedback without breaking editing.

### Phase 7 — Add hybrid rendering quality only after the vertical slice

1. Define a cache representation and generation contract before implementing the attached hybrid voxel design. Query adapter format/filtering/texture-size limits; use a manual interpolation/storage-buffer fallback or disable the optimization when unsupported. A nominal 256³ `r16float` volume is a tunable profile value, not a requirement.
2. Implement real asynchronous WebGPU cache baking from immutable scene/parameter/resource snapshots. Publish only after terminal completion, retain the previous valid cache during replacement, invalidate on all relevant generations, and never mark precomputation complete without physical work.
3. Add analytical-core/peripheral-cache selection only with a conservative error/step policy. Do not blindly blend distances if that can skip a surface; use validated error bounds, conservative step clamping, or cache initialization followed by analytical refinement.
4. Add optional foveation state for valid eye tracking and a stable head/center fallback. Track validity/fixation/saccade/lost states, filtered gaze, velocity, configurable core/ring radii, and damped recovery. Defaults such as 2%/15% must be profile values, not hard-coded guarantees.
5. Add dual-eye convergence only for valid rays, with explicit parallel, behind-eye, near-miss, confidence, and range handling. Initially use it to bias quality selection; do not use it for aggressive geometry culling or physiological depth-of-field until comfort and correctness are validated.
6. Add per-eye color/depth history only after stereo color/depth and cache generation are stable. History validity must include scene, parameter, resource, evaluation, pose, projection, foveation, cache, and display generations; invalidate on discontinuous pose, model, projection, mode, or cache changes.

**Decisions**

- `DesktopWorkspace` and `VRWorkspace` are separate composition roots. The desktop root owns all Dear ImGui and screen-space node-editor logic; the VR root owns native spatial UI and XR interaction. There will be no broad `isInVrMode` conditionalization of desktop classes.
- The core node/evaluation backend is strictly unified. Both roots use the same document identity, graph mutation/parameter transactions, validation, history, immutable snapshots, `IBackendRuntime`, render session, bounds/SDF services, capability report, and neutral freshness/lifetime policy.
- The first release allows one interactive authoring workspace at a time. Simultaneous desktop/VR editing, conflict resolution, and cross-root command ordering are deliberately excluded until a separate synchronization design exists.
- VR’s primary UI is native spatial UI. Dear ImGui may be used later for a desktop mirror or VR diagnostics/readouts only; it is not the authoring interaction model for the headset.
- OpenXR is optional and isolated. Runtime lifecycle, predicted display timing, poses, actions, haptics, swapchains, and compositor submission belong to the XR owner thread/adapter. Shared services never call OpenXR directly.
- OpenCL remains the production default until pure-WebGPU capability/parity gates and native Dawn/OpenXR interop pass. Unsupported capabilities fail visibly or use a documented lower-quality profile; they never silently change backend or semantics.
- Haptics use neutral finite-duration `HapticCommand`/`IHapticSink`/`HapticScheduler` contracts with coalescing, deduplication, priority, rate limits, stale-generation rejection, and source cancellation. OpenXR output converts finite durations to runtime durations and does not use infinite pulses for short cues.
- Generic gaze dropout is not a blink. Eye tracking and blink/pupil data are optional; tracking loss must preserve controller interaction and valid old cache/render behavior.
- Hybrid cache blending, foveation, convergence, depth composition, temporal history, functional data-flow pulses, hand tracking, and full spatial graph authoring are gated after the basic native spatial VR vertical slice.
- Rendered GPU work and acquired native images are retained until terminal completion even when a result is stale. Freshness rejection and physical cancellation/lifetime are separate concerns.

**Scope boundaries**

- Included: strict desktop/VR composition separation, shared graph/evaluation services, transaction-aware mutation/history, neutral mono/stereo render contracts, optional OpenXR lifecycle/presentation, native spatial VR controls, controller/gaze actions, world anchoring, basic model interaction, neutral haptic cues, mock runtimes, and capability/test infrastructure.
- Deliberately deferred: simultaneous interactive editing, replacing the desktop authoring UI, adapting `imgui-node-editor` into a 3D graph, complete spatial graph telemetry, functional data-flow haptics, hand tracking, vendor-specific eye-tracking behavior, aggressive thermal automation, and compositor-specific late-stage reprojection control.
- Not included in the initial implementation: making every OpenCL workflow WebGPU-capable in one change, assuming Steam/vendor APIs outside OpenXR, or using CPU readback as a production VR presentation path.

**Further Considerations**

1. The native interop spike is the hard feasibility gate. If the target cannot import or bridge OpenXR images safely from Dawn, postpone native WebGPU VR or explicitly choose a separate native Vulkan XR renderer rather than labeling it a WebGPU path.
2. Before tuning defaults, measure the target runtime’s eye-gaze/depth extensions, refresh modes, haptic frequency support, cache texture limits, thermal budget, and comfort behavior. Treat the supplied foveation radii, history weights, cache resolution, and cadence as profile starting points only.
